# 没有 Figma 付费权限，我造了座桥，让 AI 自己画完了整套设计稿

前两天我在给一个新产品画 UI，撞上了一堵墙。

我想让我的 AI 代理直接操作 Figma，帮我把设计稿画出来。结果一查，Figma 官方的 MCP server 是跟着 Dev Mode 走的，而 Dev Mode，要花钱。免费账号？门都没有。

我当时就有点不服。

这两年我写代码的方式变了。大部分时候我在跟一个 AI 代理协作，Kimi Code，Claude Code，都用过。我说目标，它动手，从读需求文档到写测试到跑命令，一条龙。所以这次做 OPC 社区平台这个新项目，我自然地想，既然代码都能让 AI 写，那 UI 设计稿，能不能也让它直接画进 Figma？

然后就撞墙上了。

其实跟我处境一样的人应该不少。很多朋友用 Figma 就是画个产品界面图，一年开不了几次大项目，犯不上为一个画图软件每月掏一笔专业版的钱。免费账号加一双手，一直这么用过来的，也没觉得缺了什么。

但 AI 代理出现之后，事情变了。以前「接口不够用」这个事无所谓，反正画画靠手。现在你想让 AI 替你干活，接口就是它的手，没有手，AI 再有想法也只能干瞪眼。

先给不熟悉这块的朋友交代一下背景。Figma 对外开放了两层接口。一层是 REST API，拿个 token 就能调，但它是只读的，你能把设计稿导出成 JSON 拿回来分析，却画不了一笔。另一层是插件 API，能力全得多，自动布局、组件、矢量路径、图片填充，什么都能干。但插件跑在 Figma 的沙箱里，必须由人亲手点开才能运行。

AI 代理的尴尬就在这儿。它站在沙箱外面，看着里面丰富的插件 API，够不着。

市面上也有一些第三方的 Figma MCP，但我看了一圈，大部分还是走 REST API 那条路。读得到，画不出。画不出，AI 就只是个观众。

于是我就寻思，能不能给沙箱开一扇窗。

答案藏在 Figma 官方给开发者留的一条缝里，开发插件可以向 localhost 发网络请求。插件沙箱里没有 WebSocket，我就用 fetch 长轮询，先连上本地一个超小的中继服务，再从中继架一条 WebSocket 给外面的脚本。一头是 AI 的终端，一头是 Figma 的画布。

桥，就这么搭起来了。

【图片·桥的工作原理图，脚本、中继、插件三层结构】

我把它叫做 figma-local-bridge，Figma 本地设计桥。已经开源了，MIT 协议，地址在文末。

先说它能干嘛，我一个个展示，每个都是真实跑过的。

第一个，最基础的。我给桥发一条 render 命令，传过去一棵 JSON 节点树，Figma 里凭空出现一张卡片。自动布局、文字样式、圆角填充，全都对。第一次看到这张卡片蹦出来的时候，说实话，有点恍惚。AI 写了那么多年界面代码，这是它第一次直接把像素画进设计软件里。

第二个，有点意思了。桥支持组件实例。我先把按钮、徽章、输入框、卡片这些做成主组件，然后让 AI 按名字引用它们。一份设计系统，几百个实例，全部跟着主组件走，改一次，全套稿子一起变。这其实就是专业设计团队的工作方式，只不过干活的是 AI。

【图片·设计系统主组件页面】

第三个，是这次真正的主角。我用它给项目画了一整套高保真设计稿。小程序端 12 屏，管理后台 16 屏，外加 64 个主组件组成的设计系统。每一屏，都是 AI 通过这座桥一个节点一个节点渲染出来的。累计 28 屏，我基本没有动过鼠标。

而且桥不光能往里写，还能往回读。我让 AI 把画好的组件规格逐个读出来，颜色、字号、间距、圆角，整理成一份设计令牌文档。之后写前端代码，所有样式值都从这份文档里引用，设计稿改一个字号，代码里跟着改。设计和实现之间，有了一条单向同步的管道。做过前端的朋友应该知道这件事的分量，多少团队栽在「设计稿和代码各长各的」这个坑上。

【图片·28 屏设计稿总览，小程序端加管理后台】

对，还没完，第四个操作才是我觉得最骚的。

桥不光能写，还能读。AI 每画完一屏，就把稿子导出成 PNG，再喂回给自己的眼睛，自己检查自己的排版。间距对不对，对齐没有，文字有没有溢出，它看图自检，不对就改，改完再渲，直到它自己满意为止。

你敢信？？？

这个闭环里，已经没有什么人的事了。我坐在旁边，像个甲方，只负责说「这儿再往左一点」。

当然，过程远没有这么丝滑。坑一个没少踩，我挑几个印象深的讲讲。

最离谱的一个，Figma 网页版不能加载开发插件，必须装桌面客户端。我一开始在浏览器里折腾了半天，插件怎么都导不进去，差点怀疑人生。而且 macOS 打开文件选择框默认不显示隐藏目录，我把插件装在隐藏目录里，死活选不到 manifest 文件，又把插件挪到了家目录下的普通文件夹才好。

还有 manifest 的网络白名单。localhost 只能写在开发域名那一栏，而且必须写 http://localhost:9741。写 ws:// 不认，写 127.0.0.1 也不认。报出来的错就一句话，devAllowedDomains must be a valid URL。我盯着这行字看了十分钟。。。

再有就是插件沙箱里没有 WebSocket。我一开始想用 iframe 方案绕过去，结果被 Figma 桌面端的私有网络策略直接拦死。实在绕不过去，就用了最笨也最稳的一招，fetch 长轮询。慢是慢了一点，但对官方来说这就是标准的本地开发场景，不算 hack，也不存在哪天被封号的理论风险。

这些坑，连同解决方案，我都写进了项目的 README。你大概率还会踩到新的，欢迎来开 issue，一起把这座桥修结实。

丑话也得说在前面。

这座桥不是 Figma 官方 MCP 的平替。官方那个是正规军，有文档有背书。我这个是土桥，走长轮询，读写有延迟，没有官方的稳定性承诺。Figma 哪天调整本地开发策略，它说断就可能断，这点心理预期大家要有。

而且说实话，很多人根本不需要这玩意。你不写代码，不玩 AI 代理，打开 Figma 就是用鼠标画画，那这座桥跟你一点关系都没有，我非常理解，点个关闭就行。

它是给谁准备的呢。给那些想让 AI 代理替自己做设计的人，给那些手里只有免费账号、又不愿意为了接一个 AI 每月多掏一笔钱的人。

写到这我突然想到一个事。

AI 代理跟图形软件之间，缺的从来不是能力。插件 API 什么都能画，AI 什么都能算，两边都富得流油，就是连不上。中间缺的，是一座桥。

桥这个东西，一头连着 AI 的文字世界，一头连着人类的视觉世界。把这两头接上，很多事的玩法就变了。今天是 Figma，明天可以是 Sketch，是 Photoshop，是所有曾经把自动化能力锁在沙箱里的软件。

我特别喜欢「磨平一些信息差」这个说法。免费账号和付费账号之间隔着一堵墙，AI 和画布之间隔着一堵墙。墙不会自己倒，但我们可以自己造门。

figma-local-bridge 已经开源了。

用法简单到离谱。装插件，起服务，在 Figma 里跑一下插件，三步。你的 AI 代理，Claude Code 也好，Kimi Code 也好，Cursor 也好，只要能在终端里执行命令，就能通过它读写你的 Figma 画布，渲染界面、实例化组件、导出图片、搭设计系统，都行。

```bash
npm install -g figma-local-bridge
npx figma-bridge install-plugin   # 安装插件到本地
npx figma-bridge server           # 起中继服务
npx figma-bridge doctor           # 自检，全绿就能用了
```

代码和文档都在 GitHub，搜 figma-local-bridge 就能找到。如果它帮你省下了哪怕一个月的会员钱，或者让你的 AI 代理第一次「看见」了自己的设计稿，回来给个 star，就够了。

开头我说，AI 站在沙箱外面，看着里面，够不着。

现在，它有桥了。
